# Billing engine

`packages/billing` decides what is printed on a customer's bill and filed with
the tax authority, offline, on a device nobody can patch until it reloads. It
is the one package where "probably right" is a bug. The rules are TRD §6.1;
this skill is how to change them without breaking them.

## Steps

1. **State the rule first.** Write down, in paise, a worked example of the
   change before touching code — the inputs, every intermediate line, the
   grand total. If the rule is a judgement (GST on service charge, a rounding
   direction), it needs an ADR via the `adr` skill and, for tax law, a CA's
   confirmation recorded in it. Done when a person can check the example by
   hand.

2. **Add the golden file.** The worked example becomes a golden case in the
   package's golden fixtures: input and expected output as JSON, amounts as
   integer paise strings. **Golden files are written by a person, never
   regenerated by the engine.** Done when the new case fails against the
   current code (or, for a refactor, passes unchanged).

3. **Change the engine** under these constraints:
   - Pure and deterministic: no I/O, no `Date.now()`, no randomness, no
     environment reads. Time and outlet settings are arguments.
   - `bigint` paise only. `round_half_up` is the only rounding, and lives in
     one function.
   - Tax per line, then grouped by rate. CGST = `round_half_up(tax / 2)`,
     SGST = `tax − CGST`, per line.
   - Order discount applied to taxable value **before** tax, split pro-rata
     by largest remainder so line discounts sum exactly to it.
   - Round-off to the rupee on its own line, never beyond ±50 paise.
   - Composition / unregistered: no tax lines, "Bill of Supply".
   - The output carries everything the server needs to re-run it and compare.
   Done when the golden case passes.

4. **Hold the invariants.** Every property in the package's fast-check suite
   still passes, and a new rule adds its own property: totals reconcile,
   CGST + SGST = tax per line, discounts sum exactly, no negative line,
   |round-off| ≤ 50, same input → same output. Generators yield integer paise
   only. Done when the properties pass at the suite's run count.

5. **Coverage and red.** Branch coverage stays at **100%** (the runner fails
   the build below it). Break the change on purpose — flip a rounding
   direction, drop the remainder step — and watch golden **and** property
   tests go red. Done when both have been seen red.

6. **Re-validation.** If the output shape changed, the contract fixture for
   the re-validated invoice changes with it, and the API's re-validation test
   still passes against the new fixture. An old POS build may still send the
   old shape: the server stores and flags it, never drops it. Done when the
   `billing` case and the contract case are updated (`test-case` skill) and
   `docs/log.md` has an entry.
