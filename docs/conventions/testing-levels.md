# A promise is tested at the lowest level that can falsify it

Every test exists to hold one **promise** — a sentence the product keeps, such
as "a cancelled invoice keeps its number and is never deleted" — and sits at
the lowest level where breaking the code would turn it red. The promises are
written down first, as numbered test cases (the `test-case` skill), and each
case names its tests or says **GAP**. A promise nobody can point a test at is
either not a promise or not tested, and the catalogue says which.

Adopted from ghatnaghar, whose central lesson carries over unchanged: three
faults there survived every unit test and were found only by running the
stack, and all three sat on a seam where the test on each side used a fake.
**A seam covered on both sides by fakes is not covered.** Bhojnalya has more
seams than most — browser database ↔ outbox ↔ sync API ↔ Postgres under RLS ↔
socket ↔ another device — so the rule matters more here, not less.

## The levels

| Level | What it can falsify | Real | Faked | Lives in | File |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Unit** | A decision inside one module | the module | collaborators it merely calls | beside the source | `*.test.ts` |
| **Component** | What a user sees and does on one rendered screen | React tree, router, i18n, store, query client, local DB (emulated) | the network, at the HTTP boundary | beside the source | `*.test.tsx` |
| **Integration** | Behaviour that *is* a real dependency's behaviour | Postgres, the browser DB engine, the socket server | nothing the promise depends on | beside the source | `*.int.test.ts` |
| **Contract** | Two sides of a wire agreeing | one shared fixture file | each side's partner | `packages/contracts/fixtures/` + both sides | `*.contract.test.ts` |
| **E2E** | One app's whole path, to the real API and back | browser, app, API, Postgres | who is signed in | `apps/<app>/e2e/` | `*.e2e.ts` |
| **User story** | A person's goal across apps and devices | everything | the aggregator's middleware (a recorded partner) | `test/stories/` | `*.story.ts` |
| **QA** | What only a person can see | real devices and printers | nothing | `docs/qa/` | dated run |

### Unit

The behaviour is a decision inside one module, and every input it depends on
can be handed to it directly. No database, no network, no DOM.

What belongs here: the **billing engine** in full, Zod schemas, invoice-number
formatting and financial-year arithmetic, business-day cut-off, idempotency-key
and UUIDv7 helpers, Zustand stores, sync-op ordering, retry and backoff
arithmetic, error-envelope mapping, `en-IN` currency formatting. A unit test
may fake a collaborator it merely calls; it may not fake the thing under test.

**The billing engine has a stricter bar** (it is the one package where a bug is
printed on a customer's bill and filed with the tax authority):

- **100% branch coverage**, enforced by the runner's thresholds, so the build
  fails rather than a report going unread.
- **Property tests** with fast-check, run on every invariant the engine
  claims: Σ lines + tax + service − discount ± round-off = grand total;
  CGST + SGST = tax on every line; line discounts sum exactly to the order
  discount; no line goes negative; round-off never exceeds ±50 paise; the same
  input always yields the same output. Generators produce **integer paise**
  only — a generator that can produce `0.1` is testing a different engine.
- **Golden files**: hand-checked invoices (inclusive × exclusive × discount ×
  service charge × composition, plus the boundary rows) stored as JSON input
  and expected output, checked by a CA or against a reference bill once and
  then never regenerated by the code under test. A golden file the code
  rewrites when it disagrees is a snapshot of the bug.

### Component

The behaviour is what a user sees or does on a rendered tree: an item added to
the cart, an error replacing a field's hint, Cancel bill hidden for a cashier
without the permission, "Print bill" disabled while the device clock is behind.
Rendered with Testing Library under the real router, real i18n, a real query
client (`retry: false`) and a fresh store, driven with `user-event`, queried by
role and label — as a user finds things.

The network is faked with MSW **at the HTTP boundary and nowhere deeper**, so
everything between the tap and the request is real. The POS's local database
runs on an in-memory IndexedDB implementation, fresh per test. That makes it
real Dexie on an emulated engine: good enough to show a screen reading what it
wrote, not good enough to prove durability (that is e2e and QA).

### Integration

The behaviour *is* the interaction with a real dependency, so faking the
dependency fakes the assertion. These cannot be observed against a stub,
because the stub is where the behaviour would have to be reimplemented:

- **Row-level security** — a request scoped to tenant A reading, updating or
  inserting a tenant-B row gets nothing or an error, **for every tenant
  table**. The suite discovers the tables from the catalogue (every table with
  a `tenant_id` column) rather than from a hand-kept list, and fails on a
  table that lacks the policy or `FORCE ROW LEVEL SECURITY`. A new table
  without isolation turns CI red without anyone writing a test for it.
- **Append-only financial tables** — `UPDATE` and `DELETE` on invoices,
  invoice lines and payments are refused to the application role.
- **Idempotent sync** — the same batch pushed three times applies once;
  ops apply in device-sequence order; a mismatched invoice is stored and
  flagged `needs_review`, never dropped.
- **The device invoice counter** — the counter and the invoice are written in
  one local transaction, so an aborted transaction leaves neither (browser DB
  engine, emulated).
- **Jobs** — an aggregator call that fails is retried with backoff and lands
  in the dead state after the last attempt.
- **Migrations** — every migration applies forward on an empty database.
- **Sockets** — a real socket server in-process with a real client: a client
  joins only its outlet's room, and an event reaches it.

Postgres runs in a throwaway container (Testcontainers, the same major version
production pins). **The tests connect as the application role**, never as the
owner or a superuser: both bypass RLS, so a cross-tenant test run as owner
passes while checking nothing.

### Contract

Where two parts of the system meet on a wire, one **fixture file** in
`packages/contracts/fixtures/` is the arbiter and *both* sides assert against
it: the POS's outbox writes a sync batch that equals the fixture, and the API
accepts that fixture and applies it. Renaming a field on one side turns that
side red and leaves the other green, which is the right shape — the file is
the arbiter, not either module. Documents are compared, not bytes.

The contracts that get one: the sync push and pull bodies, every socket event
payload, the error envelope, the invoice the POS hands the server for
re-validation, and **recorded middleware webhooks** (real payloads captured
from the aggregator middleware's sandbox, with their signatures).

### E2E

The behaviour is a property of one app's whole path and no single part owns
it: a bill rung up on the POS arrives at the API and comes back in the day's
report; a menu item edited in admin shows on the QR menu. Right when the
likely bug is a mismatch *between* parts — a field the app sends under a name
the API does not read, a route the router and a redirect spell differently.

Playwright drives **Chromium and WebKit at a tablet viewport** (and a phone
viewport for the QR menu) against the local stack: real API, real Postgres.
Nothing is faked but sign-in: the test starts from a stored session.

What an e2e test may assume, and must do:

- The local stack is up. The run refuses to start, naming the command, when
  the API does not answer.
- It **provisions its own tenant and outlet** through the platform-admin API
  and never reads data a seed or an earlier run left. Tenant isolation makes
  this cheap and makes parallel runs safe.
- Offline is `context.setOffline(true)`, never a mocked `navigator.onLine`.
- It lives in `apps/<app>/e2e/`, named `*.e2e.ts` so Vitest never picks it up,
  and its `describe` names the case it covers (`"api 0012 …"`).

### User story

The behaviour is a person's goal, and reaching it crosses apps and devices: a
guest orders from the QR menu, the cashier accepts on the POS, the cook marks
it ready on the KDS, the guest sees "Ready", the cashier settles. No single e2e
test owns that, and in ghatnaghar the user-story sweep was what found the one
defect that made the product *unusable* rather than incomplete — every part
worked, and the journey dead-ended.

- One **browser context per actor**, each with its own device and viewport:
  cashier (tablet, POS), cook (tablet, KDS), guest (phone, QR menu), owner
  (desktop, admin). Never one page playing two people.
- The aggregator middleware is played by a **companion** that posts recorded,
  correctly signed webhooks to the API and records what the API sends back. It
  is a real participant over HTTP, not a mock inside the API.
- Every story test asserts **what each actor sees and what the server
  stored**, read back through the API without the UI.
- The offline journey is the headline: bill N times offline, kill the tab
  mid-sync, reconnect, and assert zero lost and zero duplicated invoices,
  contiguous numbers within the device series, and server totals equal to the
  POS totals, invoice for invoice.
- Lives in `test/stories/`, named `*.story.ts`; its `describe` starts with the
  story or journey ID from `docs/requirements/user-stories.md`
  (`"US-QR-03 …"`, `"Journey 2 …"`), and that table's `Cov` column names it
  back.

### QA

A person (or an agent driving a browser) follows a case's **Procedure** on
real devices and records what they saw in a dated run under `docs/qa/`. It
catches what no other level can see today: an 80 mm or 58 mm print layout,
the browser's print dialog, storage surviving an iPad PWA being closed,
touch-target sizes on a low-end Android. The device matrix is the TRD's:
Windows Chrome and Edge, Android Chrome (low-end), iPad Safari as an
installed PWA. A run is a dated record and is not edited afterwards.

QA is not a substitute for a lower level. A defect QA finds gets a test at the
lowest level that can catch it; QA keeps only what is purely visual or
physical.

### Budgets are gates, not tests

The bundle budgets are checked by the build, not by a test level: the QR menu
under **120 KB gzipped JS**, failing the build when it goes over. Interaction
budgets (add item under 100 ms, KOT to KDS under 2 s) are measured in the e2e
and story levels as a positive bound with generous headroom — never as a tight
timing assertion that fails under load.

## Choosing a level

Push a promise **down** until the real thing would no longer be involved, then
stop. Pushing it upward buys nothing and costs a slower, flakier test. Pushing
it downward past that point produces a test that passes while production is
broken.

| Promise | Level | Why not lower |
| :--- | :--- | :--- |
| Inclusive 5% on ₹105.00 is ₹100.00 + ₹5.00 | unit | — |
| An invoice number is `{PP}{DD}/{FYFY}/{NNNNNN}`, ≤ 16 chars | unit | — |
| An invoice at 1 April 00:10 IST is in the new FY | unit | — (clock injected) |
| Cancel bill is hidden for a cashier | component | needs a rendered tree |
| Tenant A cannot read tenant B's invoice | integration | the policy *is* Postgres |
| A sync batch pushed three times applies once | integration | uniqueness is a constraint |
| The POS's batch is what the API parses | contract | two modules, one wire |
| A bill rung up offline appears in the Z-report | e2e | three parts, one app |
| QR order → accept → KDS ready → guest sees it | user story | three apps, three people |
| A 58 mm bill does not clip the GSTIN | QA | only a printer shows it |

Where a promise is worth checking twice — the rule as a unit test, the wiring
end to end — both appear in the case's Coverage, and the duplication is
deliberate.

## What a test must not do

**Assert a contract against a literal, never against itself.** A test that
compares `EVENTS.KOT_READY` to `EVENTS.KOT_READY` passes after any typo. Where
a name is part of a contract — a socket event name, an error code, a JSON
field, an invoice number, a route path — write the literal: `"kot.ready"`,
`"AB01/2627/000001"`.

**Use paise, as integers, everywhere money appears.** Fixtures, generators and
expectations are integer paise (`10500n`), never rupees as decimals. A
fixture that says `105.0` tests a code path production never takes.

**Never depend on the machine's clock or time zone.** Inject the clock. The
suite runs with `TZ=UTC`, so a developer in India cannot pass a test that only
works in IST; IST is asserted explicitly at the boundaries that matter — 31
March 18:29:59Z and 18:30:00Z (the FY change), and the outlet's day-end
cut-off either side.

**Let the body check everything the name promises.** A test called
`refuses a cross-tenant read` that only asserts a non-2xx status has not
checked that no row came back.

**Do not fake both sides of a seam.** If the POS's fake API and the API's fake
POS are the only things exercising the sync contract, it is untested. One side
must be real, or the seam needs a contract fixture or an e2e case.

**Never test RLS as the owner.** See Integration: a superuser or table owner
bypasses every policy, and the test goes green having checked nothing.

**Do not trust a cached pass.** Turborepo caches task results. Integration,
contract, e2e and story tasks are **uncacheable**; a green run against a
database since rebuilt proves nothing.

**Prove a negative with a control, never a sleep.** "Wait 500 ms and check no
KOT reached the kitchen" is a guess at how long nothing takes. Do something
that *must* produce an observable effect, wait for that, and the thing that
should not have happened has had its chance. For debounce and timeouts, fake
the timers and advance the clock exactly.

**Do not assert a negative at a moment defined by a racing counter.** Waiting
for a retry counter to reach *n* says nothing about *n+1*, which can land
between the wait and the assertion. Make the condition hold for as long as the
assertion needs it — a fake that fails **until released** — rather than timing
the window.

**Query the way a user reaches the element.** `getByRole`, `getByLabelText`,
`getByText` first; a `data-testid` only where nothing a user perceives
identifies the element. A test pinned to a Tailwind class breaks on a restyle
and passes on a broken label.

**Reset shared state per test.** A fresh store, a fresh in-memory IndexedDB, a
fresh query client per test; a fresh tenant per e2e or story test.

**See it red.** Every new test is watched failing once: break the code on
purpose (flip the comparison, drop the field, skip the transaction), run it,
watch it go red for the right reason, restore. A test never seen red may be
testing nothing.

## Pinning a gap

Some promises the product makes are not kept. A skipped test rots and a
failing test gets deleted, so a gap is pinned by **asserting what the code does
today**, in a test whose name begins `GAP:`, with a comment naming the
**promise** it contradicts (the case, the ADR) and a failure message telling
the next person to invert the test and close the case. It passes on the
unfixed product and goes red the moment someone fixes it.

`grep -rn "GAP:"` is then the list of promises the product states and does not
keep, and it cannot drift from the code, because it is the code. Do not use
this for a feature that does not exist yet — that is an absence, recorded in
the catalogue, not a gap.

## Running them

Bhojnalya is pre-code. The scaffold (TRD §4.3) must wire these root scripts,
and `CLAUDE.md` gets the real commands once they exist:

| Script | Runs |
| :--- | :--- |
| `pnpm test` | unit + component, every package |
| `pnpm test:integration` | integration + contract (needs Docker for Testcontainers) |
| `pnpm test:e2e` | every app's e2e, against the local stack |
| `pnpm test:stories` | user-story tests, against the local stack |

## What CI runs

A level nobody runs is a level that does not exist, so CI runs every level from
the first commit that has one: unit, component, integration and contract on
every push; the bundle budget gate on every build; e2e and stories in a job
that brings the Docker Compose stack up, waits until the API answers (not
until compose returns), and dumps the stack's logs on failure. QA is the only
level CI cannot run, and the release checklist names the latest dated run.

## Why it is worth a rule

- **Pro**: the level is a property of the promise, not of what was convenient
  to write, so placement can be reviewed before the tests exist.
- **Pro**: deliberate duplication becomes legible — a recorded choice, not an
  accident.
- **Con**: "the lowest level that can falsify it" is a judgement two people
  can disagree about. The rule narrows the argument; it does not settle it.
- **Con**: e2e and stories need the whole stack, so they are slow. That is
  why they hold journeys and seams, and the arithmetic stays in units.
